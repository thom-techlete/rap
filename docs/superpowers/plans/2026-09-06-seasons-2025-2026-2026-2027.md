# Season-Based Event Statistics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use techletes-superpowers:subagent-driven-development (recommended) or techletes-superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Preserve all historical events and attendance while separating the 2025–2026 archive from a clean, selectable 2026–2027 season view.

**Architecture:** Add a `Season` model to the existing `events` app with explicit 1 August–31 July date boundaries and one active season. Add a foreign key from `Event` to `Season`, backfill existing events into 2025–2026, and make newly created events default to the active season. Centralize the selected-season lookup so dashboards, rankings, attendance views, match statistics, event lists, and admin reports use the same season boundary without deleting or rewriting attendance data.

**Tech Stack:** Django 5.2, PostgreSQL, Django templates, existing `events`, `attendance`, and `users` apps, Django migrations, Django `TestCase`.

## Global Constraints

- Keep all existing events, attendance rows, and match-statistic rows; this feature must not delete or reset historical data.
- Use the existing `events` app and project conventions; do not add a dependency or a separate season service.
- Season boundaries are inclusive at the start and exclusive at the end: `2025-08-01 00:00:00` through `2026-08-01 00:00:00`, then `2026-08-01 00:00:00` through `2027-08-01 00:00:00`, using the project timezone.
- All user-facing labels and messages must be Dutch: `Seizoen`, `2025–2026`, `2026–2027`, `Actief seizoen`, and `Archief` where applicable.
- Existing worktree changes are unrelated and must remain untouched.
- Run focused tests first and use the repository’s Django test command or documented `pytest` command; do not switch the database to SQLite for verification.
